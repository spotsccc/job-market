# AGENTS.md

## UI: Mantine (`apps/web`)

Интерфейс `apps/web` строится на [Mantine](https://mantine.dev). Тема — `apps/web/src/theme.ts`, провайдер подключён в `apps/web/src/app/layout.tsx`.

- **Минимально меняй дефолтное поведение и вид компонентов Mantine.** Сначала ищи готовый компонент и его штатные пропсы; кастомизация — только когда без неё задачу не решить.
- **Кастомизируй через пропсы, завязанные на дизайн-систему:** `gap`, `size`, `p`/`px`/`py`, `m`/`mx`/`my`, `radius`, `c`, `bg`, `fw`, `fz`, `variant`, `color` и т. п. — со значениями-токенами темы (`xs`, `sm`, `md`, `lg`, `xl`, цвета палитры), а не с произвольными числами и пикселями.
- **Раскладку собирай из layout-компонентов** (`Stack`, `Group`, `Flex`, `SimpleGrid`, `Grid`, `Container`, `Box`) вместо самописных обёрток с CSS.
- **Если пропсов не хватает**, по порядку предпочтения: `classNames`/`styles` у компонента → CSS Modules с переменными Mantine (`var(--mantine-spacing-md)`, `var(--mantine-color-blue-6)`) → изменения в `theme.ts`, если правка нужна во всём приложении. Инлайн-`style` с захардкоженными значениями и переопределение внутренних классов `.mantine-*` — не используем.
- Новые общие токены (цвета, отступы, шрифты) добавляй в `theme.ts`, а не прописывай по месту.

## Логирование

Логгер в проекте один — `log` из `@job-market/logger` (`packages/logger/src/logger.ts`).

- **Код импортирует `log` сам.** Логгер не передаётся аргументом функции, не кладётся в options, deps или контекст вызова. Сигнатура вида `fn(db, input, { log })` — ошибка.
- **Контекст модуля — `log.with(...)` на уровне модуля:** `const moduleLog = log.with({ module: 'enricher' });`. Поля конкретной записи — вторым аргументом: `moduleLog.warn('Linked content fetch failed', { kind, id, err })`.
- **Поля запроса (`traceId`) пакеты не прокидывают.** Их добавляет приложение один раз при старте через `configureLogContext` (`apps/web/src/request-logging.ts`).
- **Ошибку кладут в поле `err`:** сериализатор разворачивает её цепочку `cause`.
- **Ошибку, возвращённую значением, пишет в лог тот, кто решает, что с ней делать**, обычно вызывающий. Функция, которая вернула ошибку, её не логирует, иначе одна ошибка попадёт в лог дважды.
- Уровень и формат задают переменные окружения `LOG_LEVEL` и `LOG_FORMAT` (`readLoggerOptions`), а не код, который зовёт функцию.
- Сигнатуры в планах (`docs/plans`) подчиняются тем же правилам.

## Тесты

Тест проверяет наш код: логику, решения и связку, которые написали мы. Поведение библиотек, фреймворков и Postgres не тестируем — за него отвечают их авторы.

- **Перед тем как писать тест, спроси: упадёт ли он, если ошибёмся мы, а библиотека будет работать как задокументировано?** Если упасть он может только при поломке библиотеки — тест не нужен.
- **Не пишем тесты, которые:**
  - проверяют, что Postgres соблюдает объявленные `CHECK`, `UNIQUE`, `FOREIGN KEY`, `NOT NULL`, выбирает индекс в `EXPLAIN`, стеммит слова или разбирает синтаксис `websearch_to_tsquery`;
  - проверяют, что drizzle генерирует нужный SQL из схемы — схему и миграции сверяет шаг CI «Migrations match the schema», а применение миграций в CI ловит ошибки SQL;
  - проверяют штатные возможности библиотеки, через которые наш код просто передаёт параметр: уровни и `child` в pino, вывод pino-pretty, сериализацию `errWithCause`, валидацию zod по схеме и т. п.
- **Тестируем:** что вычисляет и решает наш код; как он сводит ошибки библиотеки к нашим типам ошибок; что наши настройки дают нужный нам результат, когда сам результат — наше решение (вес полей в поиске, состав поискового вектора, формат записи лога, upsert по нашему ключу).
- Тест-кейсы в планах (`docs/plans`) подчиняются тому же правилу.
