# @job-market/enricher

Енричер дочитывает ссылки в тексте публикации: находит ссылки, которые умеет читать, получает
содержимое страниц и дописывает его в конец текста отдельными разделами. Классификатор и
экстрактор потом видят один готовый текст: пост «Мы ищем разработчика, подробности по ссылке»
вместе с самой вакансией по этой ссылке. Сейчас читаются вакансии и посты LinkedIn, через
акторы Apify; ключ — `APIFY_TOKEN`.

## Ответственность

| Отвечает                                                           | Не отвечает                                                                   |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| поиск ссылок в тексте и раскрытие коротких (`lnkd.in`)             | запись текста и отчёта по ссылкам в базу — это `drain` в `connectors`         |
| выбор, какие ссылки читать, и пределы на один текст                | повторы после сбоя: звать ли `enrich` ещё раз, решает вызывающий              |
| чтение страниц пачкой через читателей (`readers/`)                 | очереди и расписание — это `engine`                                           |
| формат раздела в конце текста (`section.ts`)                       | решение, вакансия ли публикация, и разбор на поля — `classifier`, `extractor` |
| отчёт по каждой ссылке: прочитана, нет данных, сбой, сверх предела | клиент Apify — это `@job-market/apify`                                        |

Зовут енричер `drain` коннекторов (`readLinks` в `@job-market/connectors`) и скрипт переноса
старых постов (`apps/web/src/transfer`).

## Границы пакета

- **Г1.** `enrich` не ходит в базу и не знает об очередях. Тексты приходят аргументом, текст с
  разделами и отчёт возвращаются значением. Из `@job-market/db` ядро берёт только тип
  `LinkStatus`.
- **Г2.** Исключение из Г1 — читатель постов LinkedIn: он ищет пост в таблице `publications`
  перед запуском актора. Это кеш, он описан ниже в разделе «Кеш». Других обращений к базе в
  пакете нет, и новые добавлять не нужно.
- **Г3.** Про сайты знают только читатели. `enrich` работает с типом `Reader` и не содержит ни
  одного адреса или id актора. Новый сайт — новый читатель в `readers/` и строка в
  `createReaders`.
- **Г4.** Сбой чтения — не ошибка `enrich`. Он попадает в отчёт ссылки статусом `failed` с
  причиной, текст остаётся без раздела. `enrich` не бросает и не возвращает `Error`.
- **Г5.** Повторов внутри пакета нет. Повтор — это новый вызов `enrich` с уже дописанным
  текстом: разделы, которые есть, второй раз не читаются.
- **Г6.** Ошибку ссылки в лог пишет вызывающий (правило из `AGENTS.md`). Сам пакет пишет в лог
  только то, что решил сам: читатель постов — что база не ответила и пост читается актором, и
  что актор не смог прочитать один пост из пачки.

## Как работает `enrich`

Вызов получает массив текстов — все публикации одного опроса источника — и проходит четыре шага.

1. **Ссылки текста.** Из каждого текста берутся ссылки `http(s)://…` по порядку и без
   повторов, без знаков препинания в конце. Ссылки ищутся только в тексте автора: всё, что
   ниже первого раздела, пропускается. Ссылка, для которой раздел уже есть, считается
   прочитанной.
2. **Короткие ссылки.** Ссылки `lnkd.in` раскрываются запросом к самому сервису без перехода:
   берётся адрес из `Location`. Раскрываются первые 10 коротких ссылок текста
   (`MAX_SHORT_LINKS_PER_TEXT`), одинаковые ссылки разных текстов — одним запросом, все запросы
   идут одновременно. Ответ без редиректа — «нет данных»: так `lnkd.in` отдаёт мёртвые ссылки
   и заглушку перед внешними сайтами. Сеть, таймаут 10 с, 429 и 5xx — сбой.
3. **Выбор страниц.** Каждую ссылку (короткую — по адресу, куда она ведёт) по очереди
   показывают читателям; её получает первый, кто узнал. Читаются первые 3 узнанные страницы
   текста (`MAX_LINKS_PER_TEXT`); страница, у которой раздел уже есть, тоже занимает место
   среди трёх. Две ссылки на одну страницу — одна страница и один раздел.
4. **Чтение и запись разделов.** Каждый читатель получает все свои id со всех текстов одной
   пачкой — один запуск актора на читателя за вызов; читатели работают одновременно.
   Прочитанное дописывается в конец текста:

   ```text
   <текст автора>

   --- Вакансия LinkedIn по ссылке https://www.linkedin.com/jobs/view/4479627327/
   Senior Backend Engineer · Acme · Berlin
   <описание вакансии>
   ```

   Раздел подписан ссылкой как в тексте автора, короткая остаётся короткой. Раздел вместе с
   заголовком — не длиннее 8000 символов (`MAX_SECTION_LENGTH`).

### Отчёт по ссылке

`enrich` возвращает по каждому тексту `{ text, links }`. В `links` — каждая ссылка текста автора
один раз, в порядке текста.

| Статус        | Что значит                                                                           |
| ------------- | ------------------------------------------------------------------------------------ |
| `read`        | раздел дописан сейчас или уже был в тексте                                           |
| `no_data`     | читатель ответил, но читать нечего: страницы нет, пост удалён, вакансия без описания |
| `failed`      | сбой: актор, сеть, ответ не по схеме; причина — в `error`                            |
| `over_limit`  | узнанная страница сверх трёх или короткая ссылка сверх десяти                        |
| `unsupported` | ни один читатель ссылку не узнал                                                     |

У короткой ссылки, которая не раскрылась, `reader` равен `short-link`. Сбой читателя — сбой
всех его id в этом вызове, у других читателей страницы читаются. Читатель, который бросил
исключение вместо ошибки значением, считается упавшим так же.

### Читатели

| Читатель        | Ссылки                                                                          | Актор                             |
| --------------- | ------------------------------------------------------------------------------- | --------------------------------- |
| `linkedin-job`  | `/jobs/view/<id>`, `/jobs/view/<слова>-<id>`                                    | `apimaestro~linkedin-job-detail`  |
| `linkedin-post` | `/posts/…-activity-<id>…`, `/feed/update/urn:li:activity:<id>`, то же с `share` | `apimaestro~linkedin-post-detail` |

Раздел вакансии — «название · компания · место» и описание. Раздел поста — автор со ссылкой
на профиль и текст. Читатель вакансий принимает не больше 100 id за вызов (`MAX_JOB_IDS`):
больше актор не берёт, а пачку на части енричер не режет.

## Кеш

Чтение страницы актором стоит денег, поэтому то, что уже лежит в базе, второй раз не читается.
Сейчас кеш есть в одном месте.

**Читатель постов LinkedIn.** Перед запуском актора он ищет посты в `publications` по
`connector = 'linkedin'` и `external_id`: пост, который коннектор linkedin уже собрал, берётся
из базы вместе с автором, от текста отрезаются дописанные разделы. Актор получает только
остальные id.

- Пост найден, но текста в нём нет — «нет данных», актор не запускается: лучше он не прочитает.
- База не ответила — предупреждение в лог, все посты читаются актором. Сбой кеша чтение не
  роняет.
- Ссылка вида `share` в базе не находится никогда: посты лежат по activity id, а share — другой
  id того же поста. Такие посты всегда читает актор.

**Чего нет.**

- Читатель вакансий кеша не имеет: вакансия, на которую ссылаются пять публикаций из разных
  опросов, читается пять раз.
- Прочитанное актором нигде не хранится отдельно. Тело раздела есть только внутри текста
  публикации, по id страницы его не найти.
- Енричер не знает, новая ли публикация. Если коннектор вернул пост, который уже есть в базе,
  `drain` всё равно читает его ссылки, а запись потом пропускает публикацию как известную.
  Это место `drain`, а не енричера.

**Почему общего кеша нет.** Мест, где подошёл бы кеш «id страницы → тело», в коде два — оба
читателя этого пакета. Общая обёртка ради двух читателей избыточна, а таблица прочитанных
страниц окупается, только если одна страница часто встречается в разных публикациях. Долю
повторов показывает запрос:

```sql
SELECT reader, count(*) AS pages, sum(n) AS links, sum(n) - count(*) AS repeats
FROM (
  SELECT reader, coalesce(target_url, url) AS page, count(*) AS n
  FROM publication_links
  WHERE status = 'read' AND reader IN ('linkedin-job', 'linkedin-post')
  GROUP BY reader, page
) AS pages_by_reader
GROUP BY reader;
```

`repeats` — сколько чтений сэкономил бы кеш. Запрос занижает: одна страница по ссылкам с
разными параметрами считается разными. К кешу стоит вернуться, если повторов заметная доля
или появился третий платный читатель. Тогда: таблица «читатель + id → тело, когда прочитано»,
обёртка над `Reader` в этом пакете без базы и реализация хранилища снаружи, а поиск по
`publications` из Г2 становится одним из её слоёв и уходит из пакета.

## API

| Что                                       | Зачем                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| `enrich(texts, options)`                  | тексты с разделами и отчёт по ссылкам; `options.readers` — читатели по порядку  |
| `createReaders({ apifyToken })`           | все читатели; порядок — кто первым получает ссылку, которую узнали несколько    |
| `Reader`                                  | контракт читателя: `kind`, `label`, `parseUrl(url)`, `fetch(ids)`               |
| `Enrichment`, `LinkReport`                | ответ `enrich` по одному тексту и отчёт по одной ссылке                         |
| `EnrichOptions`, `ExpandShortLink`        | второй аргумент `enrich`; `expandShortLink` подменяет раскрытие коротких ссылок |
| `MAX_LINKS_PER_TEXT`, `SHORT_LINK_READER` | предел страниц на текст и имя читателя у нераскрытой короткой ссылки            |
| `fakeReader` из `./test-utils`            | читатель без внешних запросов для тестов енричера и тех, кто его зовёт          |

```ts
function enrich(texts: readonly string[], options: EnrichOptions): Promise<Enrichment[]>;

type Reader = {
  kind: string;
  label: string;
  parseUrl: (url: string) => string | null;
  fetch: (ids: readonly string[]) => Promise<Error | ReadonlyMap<string, string>>;
};
```

Id, которого нет в ответе `fetch`, — «нет данных». `Error` — сбой всех id пачки.
