# @job-market/extractor

Экстрактор: достаёт из публикации, которую уже признали вакансией, её роли — поля строки
`vacancies` и места словами текста. Модель отвечает по zod-схеме (structured outputs через Vercel
AI Gateway), профессию выбирает из дерева `occupations`, а код нормализует ответ. Места к
гео-справочнику сводит не экстрактор, а `locateVacancies` пакета `@job-market/geo/server` (П16).

## API

| Что                                                                       | Зачем                                                                                                                                                             |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `extract(publication, { occupations, model? })`                           | роли публикации в порядке текста после нормализации (П10–П15); ответ не по схеме, роль без названия, ноль ролей (П5) или сбой провайдера — `Error` значением (E3) |
| `ExtractedRole`, `ExtractOptions`                                         | роль — поля `VacancyToSave` со `schemaVersion` 2 и `places` словами текста; опции — дерево профессий и модель                                                     |
| `EXTRACTOR_MODEL_ID`, `defaultExtractorModel`                             | модель по умолчанию через AI Gateway; ключ — `AI_GATEWAY_API_KEY`, на Vercel — OIDC-токен деплоя                                                                  |
| `vacancySchema(tree)`                                                     | схема ответа модели: профессия — `z.enum` id действующих узлов дерева (П12, П19)                                                                                  |
| `normalizeVacancy(vacancy)`                                               | нормализация роли модели (П10, П11, П13–П15)                                                                                                                      |
| `occupationEnum`, `occupationsPrompt`, `ancestors`, `isLeaf`              | дерево профессий: перечисление схемы в порядке пути (E4), строки промпта, предки узла, лист ли узел                                                               |
| `OccupationNode`, `ModelVacancy`, `ModelPlace`, `Salary`, `ApplyChannels` | типы узла дерева и ответа модели до нормализации                                                                                                                  |

Дерево профессий приходит от вызывающего: набор проверки берёт снимок `eval/occupations.json`,
перенос читает базу. Вызов модели — без рассуждений, не дольше 60 с вместе с повторами AI SDK.

## Команды

| Команда                                                                                 | Что делает                                                          |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `pnpm --filter @job-market/extractor test`                                              | unit-тесты `src` и `eval`: модель подменена, база не нужна          |
| `pnpm --filter @job-market/extractor eval`                                              | прогон набора проверки настоящей моделью, отчёт — в `eval/reports/` |
| `pnpm --filter @job-market/extractor eval --case geekjobs-10533 --case synthetic-paris` | только эти случаи; `--case` повторяется                             |
| `pnpm --filter @job-market/extractor eval --compare eval/reports/<отчёт>.json`          | рядом с долей совпадений печатает разницу с тем отчётом             |

Набор проверки — размеченные посты в `eval/cases` и снимок дерева `eval/occupations.json`.
`eval` берёт `AI_GATEWAY_API_KEY` и `DATABASE_URL` из окружения или `apps/web/.env.local`: места
ответа сводятся к справочнику локальной базы тем же `locateVacancies`, что при переносе. Поэтому
`eval` в `pnpm test` не входит. Правка дерева без правки разметки (П19) роняет
`eval/cases.test.ts`.

## Правила

На номера правил ссылаются комментарии в коде.

**Роли**

- **П5.** Экстрактор получает только публикации, которые классификатор признал вакансией. Ответ
  без единой роли не проходит схему, и `extract` возвращает `Error`: это ошибка классификатора, а
  не итог экстрактора.

**Поля роли**

- **П10.** Места — списком: роль `office` (где офис) или `hiring` (откуда можно работать), город,
  страна и регион словами текста и `raw` — фрагмент текста, откуда взято место. Одно место — одна
  запись: «remote из ЕС или офис в Берлине» → `hiring` с регионом «ЕС» и `office` с городом
  «Berlin» и страной «Germany». Регион не разворачивается в страны, страна не сворачивается в
  регион; «worldwide», «откуда угодно» — место найма с регионом «worldwide». Регионы — `REGIONS`
  пакета `@job-market/geo`: их названия и описания стоят в промпте. После ответа: пустые поля —
  null, место без города, страны и региона убирается, повтор места с той же ролью (без учёта
  регистра) убирается, пустой `raw` собирается из полей.
- **П11.** Навыки: `skills` — обязательные, `niceSkills` — «будет плюсом», «nice to have»,
  «желательно»; если текст их не делит, все идут в `skills`. Имя — каноническое написание из
  промпта (React, TypeScript, PostgreSQL). Пустые и повторы без учёта регистра убираются, первое
  написание остаётся; навык из обоих списков остаётся только в `skills`.
- **П12.** Профессия — id одного действующего узла дерева, самого конкретного из тех, что
  подтверждает текст: по названию роли и обязанностям. Узлы в промпте — путь и определение.
  «Senior Frontend (React)» → frontend; разработчик без стека → engineering; не понять даже
  домен → root. Роль на стыке узлов — по названию. Уровень и технологии в профессию не входят:
  это `seniority` и `skills`. `suggestedOccupation` остаётся, только если выбранный узел не лист;
  у листа и пустая строка — null.
- **П13.** Опыт — нижняя граница лет из текста: «5+ years» → 5, «от 2 до 4 лет» → 2. Уровень без
  числа («senior») опыт не задаёт. Код округляет вниз до целого; значение вне 0–30 — ошибка
  разбора, поле становится null.
- **П14.** Языки — только те, что требуют от кандидата; язык, на котором написана вакансия, не
  требование. Код — ISO 639-1 строчными, уровень — CEFR A1 … C2 или native: «intermediate» → B1,
  «upper-intermediate» → B2, «fluent», «advanced» → C1, «родной» → native; не назван — null.
  Пустой код убирается; повтор языка — остаётся более высокий уровень.
- **П15.** Разделы описания: `responsibilities` — что делать, `requirements` — что нужно уметь и
  знать, кроме навыков П11, `benefits` — что дают. Пункт — одна фраза текста на его языке;
  раскладываются по смыслу, а не по заголовкам. Маркеры списка («•», «-», «1.») и пустые пункты
  убираются; раздела в тексте нет — пустой список.
- **П18.** Остальные поля роли — название, компания, кто нанимает, уровень, формат работы,
  занятость, зарплата, переезд, виза, отклик, `summary` — задают описания полей схемы в
  `src/vacancy.ts`. `salary.gross` — true, если сумма до налогов, false — на руки, null — текст не
  говорит; `equity` — true, если обещают опцион или долю.

**Места в справочнике**

- **П16.** Места всех ролей пачки сводятся к гео-справочнику одним вызовом `resolvePlaces` —
  функцией `locateVacancies` после экстрактора и до записи. Страна по менее точному полю — итог
  `partial`, `raw` сохраняет город; регион по менее точному полю — `resolved`. Нераспознанное
  место — строка только с `raw` и итогом `not_found` или `ambiguous`, вакансия пишется. Место
  «откуда угодно» строкой не пишется: у места найма оно ставит `isRemoteFromAnywhere`, у офиса
  отбрасывается. Сбой базы — `GeoQueryError`.

**Дерево профессий**

- **П19.** Перечисление схемы — id действующих узлов в порядке пути дерева: от `root` вглубь,
  дети узла — по id. Архивный узел и всё под ним модели не предлагаются. Узел заводится с
  `description`: по нему модель выбирает узел; id узла не меняется. Дерево меняет миграция, и в
  том же коммите обновляются снимок `eval/occupations.json` и разметка набора.

**Набор проверки**

- **П20.** Ответ сравнивается с разметкой по полям, роли — по порядку, число ролей — точно.
  Перечисления, числа, булевы, `isRemoteFromAnywhere` и `experienceYearsMin` — точное равенство,
  null равен только null. `title` и `company` — без учёта регистра и пробелов по краям.
  `employmentTypes`, `skills`, `niceSkills`, `languages` (пара код и уровень) и места (пара роль и
  ключ `placeKey`) — множества без учёта регистра с точностью и полнотой. Места ответа сводятся к
  справочнику тем же `locateVacancies`; нераспознанные в сравнение не входят. `occupationId` —
  точно, расхождение делится на «ушёл к предку», «к потомку», «другая ветка».
  `suggestedOccupation` и разделы описания — только пустые или нет; `summary` не сравнивается.
  Поле, которого нет в ответе текущей схемы, пропускается.

**Технические случаи**

- **E1.** Модель отвечает по-разному на один текст. Правка промпта — улучшение, только если поле
  выросло больше разницы двух прогонов без правок. Отчёт назван временем прогона: два прогона в
  один день не затирают друг друга.
- **E3.** Значение не из перечисления (occupation «frontend developer» вместо id `frontend`) не
  проходит схему: `extract` возвращает `Error`. Места — свободные строки: что не распознал
  справочник, остаётся только `raw` (П16).
- **E4.** Правка дерева меняет схему ответа, и structured outputs компилирует её заново. Порядок
  `z.enum` не зависит от порядка строк из базы: одно дерево — одна схема, кеш схемы у провайдера
  не сбрасывается без причины.
