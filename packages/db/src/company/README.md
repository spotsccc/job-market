# Компании

Справочник работодателей вакансий. Компания — тот, в кого нанимают, а не платформа, где вышла
вакансия: вакансия Яндекса из канала GeekJobs имеет платформу geekjobs и компанию «Яндекс».
Вакансию относят к компании ключи: домен сайта и страница LinkedIn из `company_url` и название из
`company`, приведённое к одному виду. Ни один ключ не найден — компания создаётся сама; дубли,
которые ключи не склеили, сливает владелец командой.

Таблицы `companies` и `company_keys` лежат здесь, ссылка вакансии `vacancies.company_id` — в
`packages/db/src/vacancy/vacancy.ts`, миграция — `packages/db/migrations/0011_companies.sql`.
Связи для `db.query`: `vacancies.employer`, `companies.keys`, `companyKeys.company`
(`packages/db/src/vacancy/relations.ts`).

## API

Всё экспортирует `@job-market/db` (домен входит в `src/schema.ts`):

| Что                                                              | Зачем                                                                                                           |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `companies`, `companyKeys`, `COMPANY_KEY_KINDS`                  | таблицы и виды ключей в порядке поиска: `domain`, `linkedin`, `name`                                            |
| `CompanyRow`, `NewCompanyRow`, `CompanyKeyRow`, `CompanyKeyKind` | типы строк и вида ключа                                                                                         |
| `normalizeName(company)`                                         | название в одном виде или `null` (П1)                                                                           |
| `keyOfUrl(url)`, `NOT_COMPANY_HOSTS`                             | ключ по ссылке или `null`; хосты, которые ключа не дают (П2)                                                    |
| `keysOf(company, companyUrl)`                                    | ключи вакансии в порядке поиска (П3)                                                                            |
| `matchCompany(tx, { company, companyUrl })`                      | id компании вакансии, при необходимости новой; `null` — ключей нет (П3, П4). Только в транзакции вызывающего    |
| `lockKeys(tx, keys)`                                             | advisory-блокировки ключей до конца транзакции (E1, E2); берётся перед сопоставлением нескольких вакансий сразу |
| `rematchCompanies(db, { batchSize?, publicationIds? })`          | пересчёт компаний записанных вакансий, итог `RematchSummary` (П8)                                               |
| `mergeCompanies(db, fromId, intoId)`                             | слияние дубля, итог `MergeSummary`: сколько ключей и вакансий перешло, название удалённой (П7)                  |
| `SameCompanyError`, `CompanyNotFoundError`                       | ошибки слияния, наследники `AppError`                                                                           |

`mergeCompanies` возвращает `SameCompanyError` и `CompanyNotFoundError` значением, база при этом
не меняется. Сбой базы во всех функциях — исключение. Компанию при записи вакансии ищет
`saveVacancies` (`packages/db/src/vacancy/save-vacancies.ts`, П6): вызывающий `companyId` не
передаёт. Фильтр по компании — `/vacancies?company=<id>` в `apps/web/src/app/vacancies` (П9).

## Команды

| Команда                                                                 | Что делает                                                                                                                                                                                 |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pnpm --filter @job-market/web companies:match`                         | пересчёт компаний всех вакансий (П8): печатает итог и 20 компаний с наибольшим числом вакансий — среди них видно дубли. Запускать после переноса постов и после правки `NOT_COMPANY_HOSTS` |
| `pnpm --filter @job-market/web companies:merge --from <id> --into <id>` | сливает компанию `--from` в `--into` (П7); id не uuid или ошибка слияния — сообщение и код выхода 1, ничего не изменено                                                                    |
| `pnpm --filter @job-market/db test`                                     | unit- и db-тесты модуля на тестовой базе из `apps/web/.env.test`                                                                                                                           |

Обе команды лежат в `apps/web/scripts`, базу выбирают по `NODE_ENV` (`script-env.ts`): не задан —
`.env.local`, `test` — `.env.test`, `production` — только переменные окружения.

## Правила

На номера правил ссылаются комментарии в коде.

**Ключи компании**

- **П1.** Ключ по названию — `company` в одном виде: Unicode NFKC, нижний регистр, ё → е, без
  кавычек «»"'„“”\`, пробелы схлопнуты в один. Затем, пока строка меняется, по краям убираются
  пробелы, знаки препинания и организационно-правовая форма целым словом в начале или в конце:
  ооо, оао, зао, пао, ао, ип, llc, inc, ltd, gmbh, corp, plc, co. Пустая строка — ключа по
  названию нет. Транслитерации нет: «Яндекс» и «Yandex» — разные ключи.
- **П2.** Ключ по ссылке — из `company_url`; ссылка без схемы читается как https, схема не http и
  не https — ключа нет. Хост linkedin.com или его поддомен и путь `/company/<slug>` — ключ
  `linkedin company/<slug>` в нижнем регистре; другой путь LinkedIn — ключа нет. Хост из
  `NOT_COMPANY_HOSTS` (агрегаторы, мессенджеры, формы, конструкторы страниц) или его поддомен —
  ключа нет. Иначе ключ `domain` — регистрируемый домен хоста по списку публичных суффиксов
  tldts: careers.yandex.ru → yandex.ru. Ссылка не разбирается или у хоста нет регистрируемого
  домена — ключа нет.
- **П3.** Ключи вакансии — ключ ссылки (domain или linkedin, у ссылки он один) и ключ названия;
  компания вакансии — компания первого найденного ключа в порядке domain, linkedin, name. Ни один
  ключ не найден — создаётся компания с названием `company` без пробелов по краям, а если его
  нет — домен или slug LinkedIn. Ключей нет совсем — `company_id` NULL, компания не создаётся.
- **П4.** Ключи вакансии, которых ещё нет ни у одной компании, добавляются компании вакансии.
  Ключ, который уже ведёт к другой компании, не переносится: в лог пишется предупреждение
  `company key conflict` с ключом (`kind`, `value`) и обеими компаниями (`companyId`,
  `keyCompanyId`).
- **П5.** `hiring_party` на сопоставление не влияет: вакансия агентства получает компанию по
  `company`, как любая другая. Если модель положила в `company` агентство, это чинит промпт, а не
  сопоставление.
- **П6.** Компания ищется при каждой записи вакансии в `saveVacancies`, для каждой роли, в той же
  транзакции; повторная запись роли ищет компанию заново и перезаписывает `company_id`. Перед
  этим блокировки ключей всех ролей берутся одним отсортированным списком: по ролям по очереди
  две транзакции взяли бы их навстречу друг другу.

**Слияние**

- **П7.** Слияние A в B одной транзакцией переносит все ключи и все вакансии A к B и удаляет A;
  название B не меняется. A = B — `SameCompanyError`, нет A или B — `CompanyNotFoundError` с этим
  id; в обоих случаях ничего не меняется. Других способов удалить компанию нет: на неё ссылаются
  `company_keys` и `vacancies` с FK RESTRICT.

**Пересчёт и фильтр**

- **П8.** Пересчёт проходит вакансии пачками (по умолчанию 500) по возрастанию id, каждая пачка —
  своя транзакция, блокировки всех ключей пачки берутся сразу. Компания каждой вакансии ищется по
  П3 и П4, `company_id` обновляется, только если изменился; вакансия без ключей получает NULL.
  Итог: обработано, изменено, создано компаний, без компании. Повторный запуск без новых данных
  ничего не меняет.
- **П9.** `/vacancies?company=<id>` показывает только вакансии с этим `company_id`, остальные
  фильтры и `q` работают вместе с ним; то же значение ставит поле «Компания» в фильтрах — список
  компаний, у которых есть вакансии. Над списком — чип «Компания: название» со ссылкой снятия.
  Id не uuid или компании нет — чип «Компания не найдена» и пустой список. Название компании у
  вакансии — из справочника, а без `company_id` — `company` как в тексте, без ссылки; с
  `company_id` оно ведёт на фильтр.

**Эджкейсы**

- **E1.** Два разбора одновременно пишут вакансии новой компании «Acme» — компания одна:
  сопоставление берёт `pg_advisory_xact_lock` по каждому ключу до поиска, второй разбор ждёт и
  находит компанию первого.
- **E2.** Две роли одной публикации называют новую компанию в одной транзакции — компания одна:
  вторая роль видит строки первой, повторная блокировка в той же транзакции не ждёт.
- **E3.** Домен с национальными буквами (https://яндекс.рф) — ключ в punycode,
  `xn--d1acpjx3f.xn--p1ai`: так хост отдаёт `URL`, одинаковые адреса дают один ключ.
- **E4.** Суффикс из двух частей: careers.acme.co.uk → acme.co.uk, а не co.uk.
- **E5.** В `company_url` IP-адрес, localhost или не ссылка — ключа domain нет, вакансия идёт по
  остальным ключам.
- **E6.** Пересчёт идёт, пока разбор пишет новые вакансии: курсор по id ничего не пропускает, а
  вакансии, записанные после старта, уже сопоставлены `saveVacancies`.
- **E7.** Слияние идёт, пока разбор пишет вакансию с ключом удаляемой компании — разбор ждёт:
  слияние берёт те же блокировки ключей удаляемой компании, после него ключ ведёт к оставшейся.
  Без блокировок DELETE упал бы на FK от новой вакансии.
- **E8.** `/vacancies?company=abc` — не uuid: страница проверяет формат до запроса и показывает
  «Компания не найдена»; без проверки Postgres бросил бы `invalid input syntax for type uuid`.
